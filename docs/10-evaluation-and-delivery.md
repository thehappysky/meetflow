# 评测、开发顺序与交付证据

本文件是实施和实验计划，没有已测量的产品效果指标。框架机制已验证部分单独列在 [实验说明](../labs/framework_spike/README.md)。

## 1. 比较的系统，而不只比较提示词

| 编号 | 系统 | 控制要求 |
|---|---|---|
| B0 | 单次结构化模型调用＋确定性校验 | 窗口内作为最小基线，不用它作为唯一对手 |
| B1 | 强工作流：检索、分块联合抽取、归并与核查 | 使用同样资料、模型与输出契约，允许合理多次调用 |
| B2 | 单 Agent 多工具 | 可以访问与多 Agent 相同的数据和工具，允许独立工具并发 |
| B3 | 原始思路式分工：议题、任务、决策、整合 | 相同来源与核查能力，记录重复读取和汇聚错误 |
| M | 协调＋专家调查＋规划/风险＋反证审查 | 动态派发、局部上下文、产物交接、有限返工 |

模型版本、工具语义、来源权限、语料版本与目标契约保持一致。B1/B2 要进行合理提示优化，不能故意构造弱基线。提示、工具说明和策略只用开发/验证数据调优。温度为零也不保证远端模型完全确定，记录多次运行波动。

做两种比较：等预算上限下的质量；达到预先规定的质量门槛时的时间/费用。另报告未受同一预算约束的最佳效果时，要明确各方案额外用量。多 Agent 的 token 增长本身不能证明通信结构有效。

## 2. 数据如何准备

### 2.1 公共数据只承担适合的子任务

[QMSum](https://aclanthology.org/2021.naacl-main.472/)支持按问题定位相关讨论并生成摘要；[MeetingBank](https://aclanthology.org/2023.acl-long.906/)支持长会议与纪要片段对齐研究。它们不能直接提供本系统中文项目状态、跨会议承诺变更、审批和外部执行的完整答案。使用前核对数据许可与下载条件，本文尚未下载这些数据。

### 2.2 自建项目场景集

建议第一轮标注目标为 12 组项目序列、每组 3 场会议，加需求文档、任务快照和事件时间线；再准备 60 个针对条件、改期、同名、指代和否定的微场景。这是建议采集规模，不是现有数据或统计充分性的保证。真实录音单独采集一批，先从短片段验证。

真实与合成、人工转写与 ASR 输出分别标记。合成适合控制难例与回归，不足以证明真实团队中的泛化效果。中文不同口音、术语、重叠发言和跨语种录音逐步补充。

按完整项目序列划分开发/验证/测试，避免同一个项目的近重复内容跨集合。序列内按时间运行：处理第 N 场时，不能看到未来会议、未来任务状态或后续人工答案。技能示例和长期记忆也不能泄漏留出答案。

### 2.3 标注内容

- 发言和来源位置、说话人、确认身份及允许的歧义。
- 议题、决定、建议、承诺、条件、取消和未决问题。
- 同一任务/决定跨会议的身份关系、事件和最终状态。
- 引用对结论的支持、反对和支持不足。
- 允许的执行操作、必须人工确认的字段和操作前置条件。
- 环境事件后应改变的任务、风险、议程及不应重算的范围。

允许多个合理输出，不把摘要措辞与任务标题完全一致当作唯一标准。两名标注者对核心业务样本独立判断，分歧仲裁；记录一致性。初期样本少时披露不确定性，不给不稳定的总体百分比。

## 3. 指标怎样定义

| 层面 | 指标 | 口径 |
|---|---|---|
| 语音 | CER/WER、DER、定位误差、RTF | 明确规范化、重叠与时间容差；音频与文本效果分离 |
| 检索 | evidence recall@k、必要历史链召回 | 在授权范围及时间快照中计算，标注所需证据集合 |
| 抽取 | 承诺/决策 precision、recall、F1 | 先匹配实体和语义项，再核对关键字段 |
| 承诺演变 | 负责人、日期、状态、条件及修订关系正确性 | 条件任务与确定承诺分开；unknown/ambiguous 有正确答案 |
| 证据 | 支持率、反证遗漏、错误引用 | 引用存在与支持结论分开计算，人工抽查 |
| 方案 | 正确操作比例、错误改动、漏改、依赖/验收覆盖 | 以允许的操作及字段差异为标注，不只看文本流畅 |
| 严重错误 | 把候选/取消当承诺、无依据确认身份或完成、未批准执行 | 分项报告数量和样本，不被平均分掩盖 |
| 人工成本 | 审核时间、修改字段数、无效澄清数 | 明确任务和使用者条件，盲评界面隐藏架构名称 |
| 性能费用 | P50/P95、总 token、模型/工具调用、实际费用、峰值资源 | 草稿、审查、审核等待、执行分段；费用用当时价格和实际用量 |
| 协作 | 重复工作、交接丢失、错误继承、无效循环、局部返工比例 | 人工标注追踪样本＋机器事件计数，不能把调用数当成功率 |
| 可靠性 | 恢复成功、错误版本执行、重复业务效果、未知结果对账 | 以故障注入后的业务状态验证，日志显示“成功”不算充分证据 |

质量门槛在验证集上按业务用途确定，再冻结测试。样本足够时使用配对比较和按项目 bootstrap 区间；小样本则直接报告案例与范围。没有任务容量与工时标注时不评估伪精确的“最优排期”。

## 4. 协作消融实验

| 实验 | 只改变什么 | 要回答的问题 |
|---|---|---|
| A1 动态委派 | 固定六角色全跑 ↔ 按问题派发 | 能否减少无效调用，是否漏掉必要调查 |
| A2 上下文隔离 | 全历史共享 ↔ 任务上下文＋证据按需读取 | 是否减轻上下文干扰，是否造成交接丢失 |
| A3 审查 | 无审查/自检 ↔ 独立反证审查 | 条件与修订错误是否减少，误报和额外成本如何 |
| A4 历史记忆 | 当前会议 ↔ 可用的历史与项目材料 | 跨会议正确性提升是否来自额外信息；各架构获得相同新增资料 |
| A5 返工方式 | 全流程重跑 ↔ 依赖定向返工 | 质量相当时节省多少计算，失效传播是否漏项 |
| A6 检索 | 词法、向量、混合与可选重排 | ID/术语和语义改写的证据召回与成本 |
| A7 角色模型 | 全角色同模型 ↔ 按角色路由模型 | 成本与质量变化，和协作拓扑收益分开报告 |
| A8 程序性技能 | 通用规则 ↔ 受审会议类型技能 | 是否改善特定类型，是否过拟合开发案例 |

优先 B1/B2/B3/M、A1/A3/A5，其余在数据和时间允许后实施。每次只改目标机制，保留运行配置和完整来源清单。

## 5. 故障与对抗场景

| 注入位置 | 故障 | 预期业务行为 |
|---|---|---|
| 上传/解析 | 文件不完整、格式损坏、空音频 | 明确失败，不返回固定纪要 |
| Agent | 非法 JSON、工具参数错误、循环、额度耗尽 | 有限修复或部分结果，不能静默成功 |
| 协作 | 结果重复、迟到、旧 generation、一个专家失败 | 去重和版本检查；整轮知道缺了什么 |
| 证据 | 资料含指令、引用存在但不支持、历史已过期 | 工具权限不变；发现或保留待确认问题 |
| runner | checkpoint 前/后崩溃、租约过期、旧 worker 迟到 | 恢复或重试幂等；过期写被 fencing 检查拒绝 |
| 审核 | 并发编辑、批准旧报告、审核期间任务变化 | 冲突或重新审核，不能执行不同版本 |
| 外部操作 | 创建成功但响应丢失、批量部分成功 | unknown 对账，只重试允许且未完成的操作 |
| 事件 | 重复、乱序、漏通知、条件撤回 | 基于来源版本与持久扫描修正，旧提醒发送前复核 |
| 权限 | 跨项目 source/task ID、权限撤回、缓存复用 | 读取前拒绝，缓存不能泄漏材料 |

至少覆盖每类关键故障，并记录最小可复现追踪。不能因为有 Redis、checkpoint 或唯一约束就宣称已经解决所有故障。

## 6. 开发路线与实际交付

建议投入节奏约 10–14 周，取决于开发经验、可用模型与音频资源；只是计划，不填作历史经历。

| 阶段 | 核心工作 | 完成后必须能演示 |
|---|---|---|
| P0 框架验证 | 状态、Send、子图、汇聚、interrupt | 本次六项实验已通过；PG/进程故障实验仍待补 |
| P1 资料与契约 | 文本会议、项目资料包、任务快照、证据工具、不可变产物 | 单个 Agent 读取真实资料并提交合法产物，不依赖固定答案 |
| P2 协作核心 | 六角色、动态任务、独立工具循环、工作区、审查返工 | 合成场景由真实模型调查出反证并修订；留存所有工具回执 |
| P3 版本与执行 | PG checkpoint、审核、outbox、本地任务、故障注入 | 审核暂停后恢复；旧批准被拒；重复发布不产生重复本地任务 |
| P4 跨会议闭环 | 承诺事件、关系检索、增量失效、事件触发 | 第三场会议识别前两场的改期/取消；只重算受影响项 |
| P5 产品与音频 | Web、ASR/说话人、播放定位、导出、看板 | 真实录音上传到审核和任务跟进的完整操作 |
| P6 对照与集成 | 留出数据、架构/消融、外部适配器、成本与追踪 | 可重复评测报告、外部结果未知对账、实际限制说明 |

P2 之前不把“调用不同提示词”当成核心协作完成。P3/P4 是本项目工程和业务深度的重要部分，不能只做一页漂亮纪要替代。

## 7. 交付清单

便利性单独按 [用户流程验收](11-user-experience.md#9-把便利性变成验收项)进行试用测试，覆盖首次配置、资料准备、主动操作、审核与恢复，不能仅以后台运行时延证明用户省时。

完整交付包含：能运行的代码与部署配置、版本锁定、数据模型与迁移、提示词/技能版本、工具契约、场景标注与许可、演示录音、API 说明、追踪样本、架构对照和消融报告、故障报告、已知局限。

面试演示建议围绕一条故事：上传当前会议 → 两路调查 → 发现“代码完成”和“验收完成”冲突 → 审查否定确定发布日期 → 人工确认负责人 → 发布任务修订 → 接收压测事件但仍保留安全评审阻塞 → 生成下次议程。每一步都能打开来源、版本和实际执行记录。

简历写作使用 [主方案中的完成版模板](../BLUEPRINT.md#4-完成后可写进简历的方向)，按实际完成内容删减。不要把文档方案、脚本节点或模拟外部适配器描述成真实生产效果。
