# 销售会谈系统：需求确认与首版体验设计

状态：用户已确认产品方向、角色范围、录音来源、自动处理原则与验证行业。本文将已确认内容、设计建议、当前实现分别标明。岗位首页、培训样例和具体交互为可评审方案，本轮没有据此修改产品页面或宣称已完成权限。

## 1. 已确认的目标与边界

| 编号 | 用户确认内容 |
|---|---|
| C1 | 核心服务销售主管和老板，销售也有账号，用于上传、复盘和自己的进展/承诺跟踪。 |
| C2 | 老板看全公司；主管只看所负责团队；销售只看自己。 |
| C3 | 一次谈业务的录音对应一次会谈，会议纪要为产品主线。 |
| C4 | 第一版必须支持本地文件上传，后续再考虑通话/会议平台自动接入。 |
| C5 | 上传后自动生成并保存纪要和明确的待办，只让人确认不确定信息。 |
| C6 | 管理层关心客户推进、需要介入的客户、临近约定、团队今天谈了什么。 |
| C7 | 独立质检模块按公司培训流程分析做对/失误之处，提供分数和依据。 |
| C8 | 暂不开发管理者派发任务、外部任务系统对接和客户竞品分析模块；之后有真实业务再补。历史研究资料保留。 |
| C9 | 第一版以企业软件/企业服务为验证场景：需求沟通、演示、方案报价、决策签约。 |
| C10 | 没有现成培训资料，由项目拟示例培训流程与评分口径，必须明确标为示例。 |
| C11 | 页面操作要无感、傻瓜化；工程和模型配置不能成为普通用户每次使用的负担。 |
| C12 | 基于已有会谈/进展/待办，按简报、周报模板逐字段填入，销售确认后生成可导出报告。 |
| C13 | 上传录音时标题可选，允许只上传；未命名按上传时间自动命名，实际会谈时间与上传时间分别保存。录音增删改查及各类时间标记必须完整设计。 |
| C14 | 销售报告以 Word 为主，同时可导出 PDF。会议时间不明时先生成其他内容，确认周报时集中补日期；未补的单列“时间待确认”。 |
| C15 | 销售个人区的录音可由本人删改；选中确认上报后形成中心证据记录，中心删除需由主管处理。 |
| C16 | 已上报的日期/归属/纪要有错时，由销售提出更正，主管确认后形成中心新版本，旧版保留。 |

目标闭环：录音进入 → 会谈记录自动保存 → 同一客户/商机累积进展 → 自动提取约定与关注信号 → 按岗位给管理者信息 → 按同一来源做培训质检。多 Agent 在内部完成分析、查证和审查，用户围绕客户、会谈和承诺工作。

## 2. 岗位分工的依据与适用边界

Salesforce 的销售管理资料将一线主管职责归纳为辅导培训、团队沟通、进展与业绩跟踪；McKinsey 对 CEO 职责的研究强调方向、组织和资源配置。本文据此推导首页分工，不将大型企业岗位模型当作所有中小企业的固定分工：

- [Salesforce：What is sales management](https://www.salesforce.com/sales/sales-management/)
- [Salesforce：A day in the life of a sales manager](https://www.salesforce.com/ca/blog/a-day-in-the-life-of-a-sales-manager/)
- [McKinsey：The mindsets and practices of excellent CEOs](https://www.mckinsey.com/capabilities/strategy-and-corporate-finance/our-insights/the-mindsets-and-practices-of-excellent-ceos/)

**权限范围已确认，首页重点是本项目建议。** 老板仍可查看全公司具体会谈与单项质检，只是默认先看到公司范围内的摘要和重大关注项。主管也有自己团队的汇总。不能用“老板只看汇总”替代用户确认的全公司访问范围。

## 3. 三类角色的默认首页建议

| 角色 | 首页先回答什么 | 展示层级 | 可继续进入 |
|---|---|---|---|
| 销售 | 我的客户最近谈到哪一步？哪些约定快到了？哪里值得复盘？ | 自己的会谈、客户商机、承诺与质检反馈 | 原文/录音、会谈时间线、自己的质检细节 |
| 主管 | 团队哪些客户卡住了？哪里需要我参与？哪些承诺缺少完成反馈？谁需要哪种辅导？ | 团队关注事项、客户推进变化、近期会谈和培训问题 | 商机历次会谈、原文、销售维度和具体质检 |
| 老板 | 公司近期有哪些重要推进/风险？哪些事项需要公司级资源或决策？团队有哪些共性问题？ | 全公司变化摘要、需要协调的客户、跨团队问题和质检分布 | 按团队/客户/销售下钻至具体会谈及证据 |

首页每条关注事项都应带：客户/商机、发生了什么、为什么值得看、责任销售/团队、来源会谈和更新时间。用户点击事项进入上下文，不必先在几个看板间找对象。

初始不做金额预测、成交概率或收入推断。录音没有包含的合同、回款和 CRM 数据不能自动补齐。中心汇总说明覆盖范围，例如“基于本周已上报的 18 场会谈”，而不是声称覆盖团队全部活动。未上报的销售个人资料不进入管理中心汇总。

## 4. 把用户想要的数据定义清楚

### 4.1 客户进度与推进

进度以“客户下的一项商机”为单位，串联多场会谈。同一公司可能同时讨论不同产品/项目，不能仅因客户名相同就合并商机。

示例阶段为需求沟通 → 产品演示 → 方案报价 → 决策签约。阶段是摘要，不是机械的百分比。保留以下信息：

- 上一次已经明确了什么；本次新增/改变了什么；当前仍在等待什么。
- 客户是否确认了下一步、谁参与决策、还有哪些条件未满足。
- 最新依据及相应会谈，而不仅是 AI 给一个“正在推进”标签。
- 阶段变更的证据；不确定时保留原阶段并提示确认。

“销售介绍了报价”不等于客户接受报价；“准备发资料”不等于资料已经发出；没有上传后续录音不等于业务停滞。成交/丢单等正式结果需要明确依据或人工确认。

### 4.2 哪些客户需要介入

建议先定义为有证据的关注建议，不由 AI 随意给人派任务：

| 来源信号 | 默认建议给谁看 | 信息内容 |
|---|---|---|
| 客户要求主管参加下一次讨论，或销售明确请求协助 | 主管 | 需要参与哪件事、客户原话、时间是否已定 |
| 技术问题超出销售回答能力、承诺可能超出产品依据 | 主管 | 未解决问题、已有答复、所缺资料；质检也可关联 |
| 需要跨团队资源或超出团队权限的商务条件 | 先主管；确认或规则明确后再进入老板关注 | 具体需要哪类决策，已知条件与缺失信息 |
| 历次会谈反复出现同一阻碍且有明确证据 | 主管 | 阻碍如何重复出现、最近变化，不能从沉默直接判定客户流失 |

涉及权限/金额阈值时由企业配置，首版示例不伪装成真实企业政策。老板的关注列表应保留“系统建议/主管确认”等来源标记。

### 4.3 哪些承诺快到期

会谈中的承诺记录包含：承诺内容、承诺方、相关客户/商机、约定日期或触发条件、出处、当前反馈。销售与客户的承诺分开显示。

首版建议站内展示临近约定和缺少反馈的事项；暂不对接微信/邮件或派单平台。提醒提前几天属于配置，尚未确认，不硬编码成业务事实。

没有完成反馈时显示“尚无完成记录”，不能直接指控“未履约”。销售可快速标记已完成、改期或不再继续；新会谈明确改期时更新当前约定并保留旧依据。日期不明确显示“时间待定”，不凭空生成截止日期。

这是一场会谈产生的后续事项，不包含主管新建任务、分配审批、工单流转等派单功能。

### 4.4 今天团队谈了什么

中心按已上报会谈自动形成短简报：主要客户、讨论主题、明确的新变化、未决问题、需要关注的承诺。主管默认团队范围，老板默认公司范围；销售个人简报基于自己可见资料生成，生成或导出不自动上报。

显示“今日收到/今日发生”的区别：晚上传的旧录音按实际会谈时间归属；未知会谈时间不冒充今天发生。明确当前统计仅覆盖已进入系统的资料，不按上传次数评价销售勤奋程度。

## 5. 一次日常使用的完整路径

以下为拟实施交互，非现有页面已完成能力。

| 时机 | 用户最少做什么 | 系统负责什么 | 哪些情况下才询问 |
|---|---|---|---|
| 组织首次开通 | 管理员设置团队和账号，选用/修改示例培训流程 | 绑定账号/团队/权限，保存规则版本 | 岗位、团队归属等必要管理信息 |
| 销售上传 | 在自己的账号拖入录音，标题和实际时间可补充，也可直接上传 | 自动带入销售和团队；标题为空时按上传时间命名，后台处理；有可靠依据才关联客户/商机 | 归属不明保留待归属，不阻塞上传；在确实影响使用时集中确认 |
| 后台处理 | 可以离开页面 | 转写、整理纪要、关联历史、提取承诺、质检并自动保存 | 处理失败、身份不清、关键信息冲突 |
| 销售回来查看 | 直接看结果；按需处理疑点 | 显示哪些内容已完成、哪些不确定；点击结论定位原文/录音 | 同一疑点集中问一次，允许暂时留空 |
| 主管/老板查看 | 登录后直接看自己范围内的变化与关注项 | 自动准备岗位摘要，提供追溯入口 | 只有真正需要其权限判断的事项 |

销售自己的账号使销售归属无需每次填写；主管代传录音是否首版支持、如何按人批量归属仍是未确认项，不用 AI 猜录音属于谁。本轮新增要求覆盖之前“上传前先选客户/商机”的假设：选择客户不设为上传前置步骤，无法可靠关联的录音先待归属，不能擅自合并客户或商机。

### “无感/傻瓜化”的验收候选

1. 普通用户日常无需选择 Agent、模型、演示/真实模式、评分卡版本或手动启动二次质检；相关配置放管理端。
2. 同一录音上传一次，纪要、客户进展、承诺、质检共用来源，避免另填一套会话信息。
3. 不要求逐条审核全部纪要和承诺后才能使用；明确内容自动保存，关键疑点独立列出。
4. 身份、日期或客户归属不明时只询问相应信息，不让用户重填整张表；提醒影响范围。
5. 离开、刷新、失败后能继续；不重复上传、不重复生成承诺；真实失败不能替换为假结果。
6. 主管和老板的主要事项都能直接进入关联商机/会谈，用户无需记住记录在哪个模块。
7. 未知、自动提取、人工确认和已修订状态清楚可辨；用户可以更正系统误判。

这些是具体可测的体验标准，需先用日常场景/低保真交互验证后再调整正式页面。按钮数量和耗时目标待实际操作测量，不先编造“三秒完成”等承诺。

## 6. 独立质检模块：示例培训与评分

状态：项目拟定的 B2B 软件/服务销售培训示例，不是企业实际制度或通用行业标准。

### 6.1 示例阶段流程

| 会谈阶段 | 培训期望 | 能支持推进的证据示例 |
|---|---|---|
| 需求沟通 | 了解客户现状、困难与影响，核对理解；了解相关参与者与后续意向 | 客户确认需求、同意相关人员参加演示；未提供预算可以保留未知 |
| 产品演示 | 演示与需求对应，记录反馈和未解决技术问题，说明能力边界 | 客户给出试用/验证问题或双方确认下一步验证；仅销售自述不等于客户认可 |
| 方案报价 | 解释范围、条件与价格，澄清异议，了解决策安排 | 客户确认收到/讨论方案、明确尚需解决的问题和后续沟通 |
| 决策签约 | 核对待决条件、采购/法务/交付边界与下一步 | 客户明确反馈决策安排；合同实际签署等正式状态仍需可靠依据 |

### 6.2 示例评分维度

| 维度 | 示例权重 | 做对的行为 | 可判失误的依据 | 适用条件 |
|---|---:|---|---|---|
| 需求澄清 | 25 | 围绕现状、困难/影响提问并核对理解 | 误解客户明确表达，或在完整且适用的会谈中忽略规定的核对动作 | 本次涉及需求沟通/确认 |
| 决策条件了解 | 20 | 适时询问参与者、安排与约束；未知如实记录 | 把未确认预算/身份写成确定事实，或漏掉本阶段明确必需动作 | 依阶段要求；客户不愿透露本身不是销售失误 |
| 方案与承诺边界 | 20 | 回应对应客户需求，承诺有已确认产品资料支持 | 具体承诺与产品依据矛盾，或遗漏明确必要条件 | 本次有方案/能力/交付承诺且有产品依据 |
| 异议处理 | 15 | 澄清异议原因，再提供有依据的回应或记录后续验证 | 未核实便给错误答复、回避明确异议、作无依据保证 | 本次实际出现异议；不出现则不适用 |
| 下一步清晰度 | 20 | 双方确认后续动作或明确等待条件，责任和时间如实记录 | 将销售单方建议当作双方承诺，遗漏已有明确约定 | 本次适合讨论后续安排；客户拒绝给日期不能直接扣分 |

以上是供评审的初始口径，还需逐条补齐达标/部分达标锚点与阶段适用规则后用于正式计算。无法从“未看到某句话”直接判定违规；录音不完整、身份未知、依据不足时保留无法判断。

### 6.3 每条质检结果应呈现什么

- 对应哪条培训要求、适用的会谈阶段及规则版本。
- 本次做对了什么、失误/遗漏是什么、为什么影响该规则。
- 支持判断的原话与回听位置，包括支持和反例，不只摘一句。
- 达标/部分达标/未达标/不适用/无法判断，及代码算出的得分、扣分和覆盖率。
- 一条可执行的改进建议；涉及争议时允许销售反馈、主管复核，并保存原判断与改判原因。

普通用户不逐场选择评分卡，系统按已配置阶段规则处理；阶段不明时标疑点，纪要仍先可用。模型不自行发明规则或分值。

自动评分与人工复核状态分别标明，主管重点处理争议/异常，不强迫复核每场。现有“仅已复核进入汇总”的逻辑需重新设计：若展示自动评分趋势，应标明来源、覆盖率与未复核样本，不能悄悄混合成正式绩效结论。该口径尚未实施。

## 7. 权限范围与操作权限

### 已确认的数据范围

中心的公司/团队范围作用于已上报记录，不因此获得销售未上报个人区的内容。销售另有自己的个人区。上传后自动处理/保存先发生在个人区，进入中心的边界为本人选择并确认上报，详见第11节。

| 数据 | 销售 | 主管 | 老板 |
|---|---|---|---|
| 会谈、原录音、原文 | 自己 | 负责团队 | 全公司 |
| 客户/商机及关联进展 | 自己负责范围 | 负责团队范围 | 全公司 |
| 承诺、提醒与复盘 | 自己 | 负责团队 | 全公司 |
| 质检结果与依据 | 自己 | 负责团队 | 全公司 |
| 汇总、搜索、导出入口 | 仅本人范围 | 仅团队范围 | 公司范围 |

搜索、录音 URL、导出、后台处理都必须遵守同样范围。页面切换角色不能代替真实账号身份，服务端不接受用户自行填写的角色来扩大权限。

### 尚待细化的操作权限

谁可修订原文/客户归属、确认业务阶段、复核评分、发布培训规则、邀请/转移成员、导出和删除录音，尚未由用户逐项确认。建议保留老板/管理员统一组织与规则配置、主管负责团队审核、销售维护自己的业务反馈；这不是已确认授权。

离职/转组后的历史归属、多人共同负责一个客户、主管跨团队管理等边界需要用实际业务再确定。首版不能仅靠“salesperson”姓名字符串提供权限。

## 8. 当前实现与新需求之间的差距

| 需求 | 当前实际状态 | 后续工作 |
|---|---|---|
| 三角色账号、团队权限 | 未实现；当前本地单用户 | 组织/账号/团队模型、登录与全链路访问限制 |
| 录音上传与证据 | 真实 ASR + 24 段测试完成，质量有限 | 提升转写、可靠身份核对与日常上传体验 |

| 承诺临期提醒 | 有本地任务和日期字段，无完整提醒/履约反馈链路 | 会谈承诺对象、状态修订、站内临期与缺反馈列表 |
| 岗位首页与日/周简报 | 未实现；现有首页以导入/列表为主 | 基于角色和证据的关注项、变化摘要和下钻 |

| 录音增删改查与时间管理 | 有上传/读取/播放及部分元数据，无完整修改/删除/恢复体验 | 自动命名、独立时间字段、编辑版本、权限、删除影响与恢复规则 |

## 10. 新增：销售报告与最低输入录音管理

### 10.1 销售报告的用途与流程

已确认：在供销售复盘的纪要、待办之外，系统将已整理的信息按简报/周报模板逐字段映射，销售确认后生成并导出，供销售实际使用。此功能提升销售端的直接价值，不仅向管理者提供数据。

建议日常路径：打开“我的报告” → 默认本周/企业常用模板 → 自动填入可追溯内容 → 销售核对并修改待确认项 → 确认生成 → 导出 Word 或 PDF。常用模板和字段映射配置一次后复用，不要求每周重新配置。Word 为主要交付，PDF 为同一已确认版本的另一种格式，不分别重新生成内容。Excel 不作为当前已确认首版格式。

| 模板字段示例 | 可映射资料 | 处理规则 |
|---|---|---|
| 本周客户沟通 | 周期内会谈及已确认客户关联 | 按客户/商机归纳，保留原会谈；统计范围说明清楚 |
| 主要推进 | 多次会谈之间有证据的变化 | 单方计划不能写成已完成推进 |
| 已完成事项 | 有完成记录或明确来源的承诺 | 待办中出现过不等于已经完成 |
| 未决问题/需协助事项 | 会谈未决信息、承诺条件、介入建议 | 自动提取与销售确认状态分别可见 |
| 下周计划 | 明确的未来安排、尚待确认的建议 | 已约定与个人计划分开，不擅自填写日期/负责人 |
| 签约金额、回款等 | 仅明确记录或人工补充 | 无来源时留空/待补，不编造，不把未知当零 |

“逐字段映射”不是把整篇 AI 总结塞进模板：每个字段应有候选值、来源和缺失/冲突状态。销售可就地修改；人工补充与自动提取分别留痕。只确认有争议的来源信息，报告最终确认一次，不强迫逐行重复点确认。

报告保存周期、模板版本、数据来源版本和人工修改；确认后生成一个固定版本。后续录音或承诺修订时，已有报告提示来源更新，可生成新版本，不能悄悄改写已确认报告；已导出的本地文件也不能被系统追溯修改。

### 10.2 上传最低输入与命名

已确认允许两种入口：

- 用户填写自定义标题，可描述大致时间段、讨论主题等；原文保留，不要求固定句式。
- 直接上传，系统在服务端成功接收后生成标题，如“11月11日 下午上传的会议录音”；具体日期样式和时段分界是展示建议，尚未确认。

自动名称必须含“上传”语义，不能让人误以为是该时段发生的会谈。标题中出现“昨天下午”“需求演示”等信息可作待核实线索，不能覆盖真实时间字段或擅自确认客户。无需销售每次填写所属销售、团队、模型、评分卡或分析模式。

同一天多份录音可用上传时分/短编号区分，标题不作为唯一 ID。重命名不改变上传时间、实际会谈时间、原文件及历史来源引用。文件名/文件修改时间不作为可信会谈时间。

### 10.3 时间字段及其用途

| 时间 | 意义 | 核心规则 |
|---|---|---|
| 上传时间 | 系统成功接收录音的时间 | 服务端记录，不能由重命名/重试重置成新的会谈日期 |
| 实际会谈开始/结束 | 录音对应事件的发生时间，可未知或只有日期/时段 | 与上传时间分开；说明来源和精度，不伪造精确分钟 |
| 录音时长 | 媒体解码得到的长度 | 不依赖标题；校验文件、播放和片段范围 |
| 片段时间偏移 | 原音频起点后的秒数 | 用于回听，不等同于墙上时钟；无会议起点时不换算成绝对时间 |
| 更新时间/删除时间 | 元数据修改或删除操作的发生时间 | 独立留痕，不覆盖原上传/会谈时间 |
| 报告生成/确认时间 | 本次报告操作时间 | 与报告统计周期分开保存 |
| 约定日期/触发条件 | 承诺中提取并确认的时间信息 | 不从上传日期猜相对日期，实际会议时间不明时保留待确认 |

技术上建议统一保存可换算时区的时间，按组织时区展示；用户给的只有日期/上午下午时保留该精度，不强行补秒。跨天录音、时区、周起止、年末跨年、晚上传旧录音需要专门测试。

已确认：实际会谈时间不明时，先生成报告其他内容，确认周报时集中补会议日期；未补的明确单列“时间待确认”，不冒充周期内已发生的会议。上传时间不能静默替代实际会谈时间用于客户进度、履约日期或周报周期。

### 10.4 录音增删改查的完整边界

| 操作 | 拟议行为与必须考虑的影响 |
|---|---|
| 新增 | 拖入上传、进度/失败恢复、大小/格式校验；检测相同文件，防止重试重复生成会谈与承诺；去重不能泄露无权限记录是否存在。 |
| 查询 | 依本人/团队/公司范围查找；标题/主题/已确认客户搜索；区分上传时间与会谈时间筛选；可见转写和关联报告状态。 |
| 修改 | 支持改标题、补会谈时间、校正归属；记录修改历史。转写更正保存新版本，原识别和引用仍能追溯。替换音频须建新版本并提示影响，不静默覆盖。 |
| 删除 | 已确认个人区录音由销售本人管理；中心证据须主管处理删除。销售个人区删除不级联删除中心上报版本。软删除/回收站时长、中心删除后的物理清除和历史引用保留细节仍待设计，不能把“删除”擅自实现成不可恢复全量清除。 |

删除需明确纪要、质检、商机进展、承诺、未确认报告、已确认报告的关联影响。候选方案是正常业务中隐藏/停止引用该来源，已确认报告保留版本并标记来源状态；不再提供已删除录音的播放地址。具体保留与恢复策略以用户选择为准。权限必须覆盖下载、播放、搜索和恢复，不能仅隐藏列表项。

### 10.5 新增验收场景

1. 不填标题、客户或实际时间，直接上传成功；生成明确的“上传时段”标题，实际会谈时间仍未知。
2. 今天上传上周会谈，补实际日期后进入正确周期；改标题不改变会谈/上传时间。
3. 相同文件重试不重复创建会谈和承诺；同名不同录音仍可区分。
4. 默认周报自动映射已有记录，未知金额/完成状态不被补造；销售修改确认后能按选定格式导出。
5. 修订会谈时间或承诺后，旧报告可追溯且提示来源变化；重新生成产生新版本。
6. 按最终删除策略验证录音删除及关联报告状态，原 URL 无法继续绕过权限播放；如果支持恢复，同时恢复合法关联。

本节为已确认新方向和待确认规则的记录，尚未编写相应产品代码。

## 11. 确认上报：个人工作区与中心证据边界

### 11.1 已确认的动作及本轮理解

- 上传先进入销售个人工作区，自动生成并保存该销售可用的纪要、承诺与复盘资料；销售可在自己的页面删改。
- 销售勾选对应录音，确认上报后，中心得到可作为依据引用的记录；主管看所负责团队已上报资料，老板看全公司已上报资料。
- 中心记录不随销售后来删除/改写个人记录而消失或变动。销售对中心没有直接删除权；中心删除由主管处理。
- 中心记录更正由销售提出，主管确认后发布中心新版本，旧版保留。这一点已由用户单独选择确认。

本轮据此采用“未上报个人区不进入主管/老板管理视图”的产品边界；不能因为老板能看全公司中心记录，就展示未上报个人草稿。若未来需要特殊管理访问，应另行定义，不能隐含扩大权限。

### 11.2 典型操作路径

```text
销售上传（可不填标题/客户/实际日期）
  → 个人区自动处理并保存，可复盘、整理和生成个人报告
  → 销售选择录音，查看本次上报范围，确认上报
  → 中心保存该次录音及关联依据的版本
  → 主管/老板在权限范围内查看、汇总、引用
```

“确认生成报告”“导出 Word/PDF”“确认上报”是不同动作。导出个人报告不扩大资料可见范围。上报只作用于明确选择的来源，不把未选录音或个人报告悄悄一并上报。

上报范围应清楚说明选择的录音与关联纪要/依据，不让销售反复填表。是否允许处理尚未结束的录音先上报、报告本身是否需要独立上报入口，尚未确认；未确定前不额外增加审批关卡。首次上报不自动变成“主管逐条审核全部纪要后才可见”。

### 11.3 中心证据建议采用固定版本

这是落实已确认业务规则的实现建议：个人工作副本与中心提交版本逻辑分开，中心引用固定的音频内容、元数据/会谈时间、转写版本和相关结果。底层可以去重存储，但生命周期和访问控制必须独立。

| 情形 | 个人工作区 | 中心/管理数据 |
|---|---|---|
| 未上报时修改或删除 | 本人可操作，按相应历史/删除策略管理 | 不产生中心记录或管理统计 |
| 已上报后修改标题/时间/纪要 | 个人区可以调整 | 已上报版本保持原样，提示个人/中心存在差异 |
| 已上报后删除个人记录 | 按本人操作隐藏/删除个人副本 | 中心证据仍然存在，不能因共享物理文件而被清除 |
| 销售申请更正中心内容 | 保存拟修改字段、原因及所基于中心版本 | 主管确认后生成新版本，保留旧版；拒绝则中心不变 |
| 重复点击或网络重试上报 | 显示上报结果 | 同一提交不重复增加中心会谈、承诺和统计样本 |
| 主管删除中心记录 | 不擅自同时删除销售个人副本 | 记录操作者、原因及关联影响；权限限其负责范围，后续保留/恢复政策待定 |

原音频不被纪要文字修改覆盖；替换音频是新的来源版本。报告、质检与承诺必须知道引用的是哪个中心版本，中心更正不悄悄重写已确认/已导出的历史报告。

### 11.4 需要保留的状态与时间

区分个人记录状态、处理状态、上报状态及更正状态，避免用同一个“已完成”含混表达。至少能识别：未上报、已上报、存在个人修改、更正待主管确认、中心已更新、中心已删除。

分别保存上传时间、实际会谈时间、上报时间、个人修改时间、更正申请/主管确认时间、中心删除时间。上报或更正不能让旧录音变成“今天发生的会议”；按上报时间统计的是资料进入中心的活动，不是销售实际沟通次数。

### 11.5 新增验收场景

1. 销售上传两场录音，只选择一场上报；主管和老板的中心搜索、录音地址、简报与质检统计均不泄露另一场。
2. 删除/重命名已上报的个人记录，中心原文、音频与引用仍可用且版本不变。
3. 销售提出日期更正，在主管确认前中心保持旧版；确认后产生新版，历史报告仍可追溯旧依据。
4. 两个更正同时基于旧版本提交，主管处理时能发现冲突，不用后提交覆盖先确认的版本。
5. 主管处理中心删除时能看到引用影响；销售不能通过直接请求、原播放链接或个人删除绕过中心权限。
6. Word 和 PDF 来自同一已确认报告版本；时间未补全的来源明确列为待确认，不混入确定的本周活动数量。

目前没有个人区/中心区、上报或更正审批的实现，以上均为待落地需求和验收条件。
