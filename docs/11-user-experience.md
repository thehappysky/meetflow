# 用户如何使用 MeetFlow，以及怎样检验便利性

日期：2026-10-24。本文件补充主方案的产品使用流程，尚无可交互 Web 成品或用户测试结果。文中流程与指标均为设计和待验证要求。

## 1. 对原方案的审阅结论

原方案已考虑：原文/音频定位、同页核对、明确范围的批量批准、页面断开后后台继续、按依赖局部重算、任务看板和资料不足时继续生成纪要。

原方案仍缺少：首次使用和日常使用的区别、资料维护责任、最少输入、结果先后呈现、澄清合并、不同用户的视图、低打扰跟进，以及能够证明便利性的用户测试。

原方案中的六类界面是功能清单，不应直接变成用户必须依次走完的六页流程。也不能让用户每次准备一整套历史材料、配置 Agent、理解证据版本或逐条批准全部摘要。

## 2. 三类使用者

| 使用者 | 主要操作 | 不需要承担的操作 |
|---|---|---|
| 项目维护者 | 一次建立项目、接入资料和成员、设置共享范围与通知偏好 | 每场重新上传相同历史资料 |
| 会议整理者 | 上传录音或文字、确认实际会议时间、核对重点与发布变更 | 选择 Agent、手工分配调查任务、阅读原始协作消息 |
| 任务参与者 | 查看分配给自己的任务、依据、阻塞与截止日期，更新状态 | 为了看一个任务先学习整个协作系统 |

个人使用时角色可以是同一人；团队使用时是否能批准或修改任务由项目权限决定。参会者不会因为录音里被提及，就自动获得整个项目资料访问权。

## 3. 首次使用：先得到一次结果

主入口提供“上传录音”和“粘贴会议文字”。默认归入个人项目，允许选择已有项目；不把创建复杂项目结构作为首次处理的前置步骤。

会议标题可以从文件名或内容产生草稿。时区沿用用户/项目设置并可见；实际会议时间从可靠元数据预填，或提示用户确认。文件创建时间、上传时间与模型猜测不能自动当成会议实际时间。无可靠时间时相对日期保留原话和待确认状态。

首次无需接入外部平台、维护成员别名或上传历史会议。缺少资料时，明确标记“本次仅分析当前会议”，仍提供纪要、候选任务和原文核对。系统不能展示“未发现历史冲突”来暗示已经完成并不存在的核查。

用户可以在看到第一份结果后，再选择关联项目和补充历史资料。资料范围变化触发明确的新分析版本；不把个人项目产生的结果直接混入另一个项目的共享事实。

## 4. 项目配置一次，后续会议复用

项目维护者可以上传需求文档和历史会议，导入任务，或连接一个受支持的平台。项目资料保留来源和更新状态，已有文件不要求每次重复准备。个人模式的本地看板也能完成闭环，平台连接是按需配置。

会议类型优先使用项目默认或由内容提出建议；一般用户不需要选择技能包、Agent 数量和模型。影响结果范围的选择用业务语言展示，例如“结合本项目历史资料核对”。

身份映射不是每次必须完成的全员表格。仅当未确认的说话人/称呼影响任务归属时，汇总到待确认区。用户本次确认默认只作用于本次相关内容；跨会议别名复用需要明确范围，不把声音簇标签永久绑定某个人。

## 5. 日常使用的完整路径

```mermaid
flowchart LR
    A[上传录音或粘贴文字] --> B[确认必要会议信息]
    B --> C[后台处理，可离开页面]
    C --> D[先查看纪要草稿]
    D --> E[核查完成：查看变化与待确认项]
    E --> F[确认选中的任务变更]
    F --> G[查看任务与后续摘要]
```

### 步骤 1：上传

用户选择项目并提交文件；标题、时区、会议类型和资料范围尽量沿用可见默认值。页面只突出缺失且会影响结果的字段。文件过大或格式不支持时保留已经填写的信息，给出可执行的处理说明。

### 步骤 2：处理期间不用守着页面

显示“转写中”“整理讨论”“核对项目资料”“检查任务与条件”等业务阶段，不展示 Pregel、reducer 或每个工具调用。可离开页面，回来继续查看；支持请求停止未完成处理，但已经在途的调用可能仍完成，界面区分“正在停止”和“已停止”。

有可读草稿后即可查看，继续核查的部分有明确标记。早期草稿不显示“已核查”，不能直接据此批准尚未稳定的执行方案。若允许下载草稿，文件明确标注草稿和待确认项。

深度分析更新结果时，保留用户编辑；冲突字段展示差异供选择。不能用新模型结果直接覆盖用户已经改好的内容，也不能让用户在不知道结果已变化时批准旧页面。

### 步骤 3：在一个会议页面理解结果

页面顶部首先说明本次分析范围、关键结论和需要用户处理的事项。默认结构是：

- 纪要：本次讨论和结论，可阅读、复制和导出。
- 任务与变化：新增、修改、暂停、阻塞，以及旧值到新值的差异。
- 待确认：影响正确性或执行的少量问题。

证据在侧栏按需展开，点击原文可定位音频及前后发言；无音频时定位文字。历史演变和开发追踪作为可展开入口，不要求用户离开当前审核上下文。

### 步骤 4：只解决需要判断的问题

例如界面集中提出：

> “客户通知由谁准备？” 原文称呼为“老王”。
> 选项：王芳 / 王宁 / 暂不确定。

用户选一次，更新同一称呼在本次明确关联范围内的任务，而不是收到几个 Agent 的重复问题。另一个问题可以展示：“本周五只是候选窗口，是否保留为候选？”并给出原话。

澄清由协调层按实体、字段和作用域合并，按对执行的影响排序。无法回答可选“稍后处理”，资料缺失默认不强迫用户补齐全部文档。若某操作依赖未决条件，只阻止该操作及其依赖，不阻止查看纪要或确认其他独立任务。

### 步骤 5：明确范围，一次确认

自动生成的纪要不要求逐句批准才能阅读。正式任务写入采用差异清单，例如：“新建 2 项、改期 1 项、暂停 1 项”，用户能选择、编辑或跳过具体操作，再点击“确认所选变更”。这一次就是针对所示内容的批准，不再追加内容相同的多层弹窗。

未确定负责人可以保留为待分配本地任务，是否允许同步由目标系统字段要求决定。模型的排期建议、候选条件和会议已确认承诺必须在界面上区分。

用户只修改一个字段时，重新检查受影响部分。已完成的其他操作保留回执，不要求重复执行或重复批准。尚未执行的批准能否保留，取决于操作内容、依据和前置条件是否仍一致，不能仅因界面想减少点击就沿用过期批准。

### 步骤 6：进入已有工作方式

没有外部平台时使用内置看板；已连接平台时，明确哪些任务以哪个系统为准，展示同步中、已同步和需要处理的状态。不能要求用户在两个看板中手工维护同一份状态。

普通参与者默认看到“与我有关”的任务、变更和阻塞，项目整理者可以查看全局。若采用分享链接，仍按用户权限控制，不默认把项目资料变成公开链接。

## 6. 会后跟进尽量少打扰

原始 Agent 分歧和每条工具调用不产生通知。默认在应用内汇总真正需要处理的变化，例如新待确认事项、相关任务改期、阻塞条件改变。截止提醒与外部渠道按用户设置启用。

相同事件与短时间重复变化合并；完成、暂停、取消后的旧提醒发送前复核。支持个人通知偏好与静默设置。通知说明发生什么变化、影响什么任务、需要什么动作，不只写“Agent 已完成分析”。

下一次会议准备包自动汇总未完成承诺、待确认问题和新阻塞，用户可编辑为议程。资料没有更新时明确显示最近更新时间，不能暗示进行了实时监控。

## 7. 失败时怎样使用

| 情况 | 用户看到什么 | 保留与恢复 |
|---|---|---|
| 转写失败 | 失败阶段与重试；可改用已有文字 | 原文件与表单保留，已完成产物复用 |
| 历史资料连接失败 | 当前会议结果可用，相关核对未完成 | 不把连接失败解释为没有冲突；可稍后补查 |
| 一个疑点不能确认 | 待确认项及原文，允许暂缓 | 其他独立事项仍可继续 |
| 执行期间任务被修改 | 只展示冲突操作的新旧差异 | 重新确认相关项，不让用户重做全部审核 |
| 远端结果未知 | “正在核对是否已创建”，必要时请求处理 | 不诱导反复点击创建；已成功操作有回执 |
| 浏览器离开或断网 | 回来可查当前进度和草稿 | 后台任务不依赖页面保持连接 |

错误页面不展示技术堆栈；支持追踪编号和开发详情入口。重试是否可能再次产生费用或外部效果，由真实状态决定并在相关操作中说明。

## 8. 页面结构收敛

主导航采用“会议”“我的任务”“项目”，配置放在项目设置。会议详情承载纪要、变化、待确认和证据；项目页承载历史资料与承诺演变。协作追踪属于高级/开发视图，不成为普通用户的必经步骤。

支持直接从任务跳到对应会议证据、从通知跳到具体待确认项。表单自动保存草稿；键盘可操作，处理状态有文字说明，警告不只依赖颜色，音频定位也提供文字替代。

## 9. 把便利性变成验收项

以下是设计门槛，不是已经达到的效果：

- 无历史资料、无外部连接时，能完成第一次会议整理，不被配置流程阻塞。
- 日常上传只要求录音/文字及无法可靠预填的必要信息，项目资料不重复提交。
- 用户不需要配置或认识 Agent 即可完成日常任务。
- 一项实体歧义在同一作用域内集中询问一次；暂缓有明确结果。
- 从结论到对应原文、从任务到其依据有直接入口。
- 无关未决事项不阻止阅读、导出草稿和处理独立事项。
- 一次明确范围的确认即可提交对应变更；内容变化时只处理受影响范围。
- 中途离开、网络失败、编辑冲突有可恢复路径。

邀请未参与开发的试用者完成“首次导入”“日常上传”“确认歧义”“处理一次改期”“查看个人任务”“断线恢复”等任务。记录完成率、首次得到可用结果的时间、主动步骤、资料准备时间、审核时间、修改数、误操作、重复提问和通知有效性；与人工整理流程及首次/熟练使用分别比较。

系统后台耗时、用户主动操作时间和首次配置成本分开报告。不能只证明模型运行更快，就宣称用户更省时间。目前没有 Web 原型和试用结果，因此便利性仍是待实现与验证的设计目标。
