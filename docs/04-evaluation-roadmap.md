# 评测与实施路线：怎样做完，怎样证明有效

> 本文是后续实施与评测计划。本次没有运行真实模型、音频识别或外部系统基准，没有实测的准确率、耗时或生产收益。

## 1. 先定义“成功”

生成了一份能解析的 JSON，只证明格式符合要求。会议助手还需要回答：信息是否完整，结论是否被支持，负责人和日期是否正确，任务有没有真实执行。

| 层次 | 成功定义 | 不能混用的概念 |
|---|---|---|
| 转写 | 真实录音产生有效转写，记录识别误差 | 演示文本不算转写成功 |
| 抽取 | 正确覆盖会议中的事实、决策与任务 | 格式成功不等于语义正确 |
| 证据 | 引用可定位且支持对应陈述 | 引用存在不等于事实受到支持 |
| 审核 | 用户确认具体版本与范围 | 点击按钮不等于批准新版本 |
| 外部执行 | 目标系统确认操作结果 | 本地入队不等于远端创建成功 |
| 跟进 | 状态变化和提醒记录可验证 | 计算了提醒数量不等于真实调度 |

## 2. 数据集与标注

文字版起步建议准备 30 个完整场景，分为 10 个开发、10 个验证和 10 个留出测试场景。开发集调整提示词；验证集选择方案；留出集冻结后才用于报告。这个数量是开始工作的建议，小样本结果必须明确范围。

同一会议的片段和近似改写放在同一集合，避免开发内容泄漏到测试集。保留至少三场长会议场景，专门测试跨块改口、取消和上下文预算；把同一短句机械重复多次不能替代真实长会议评测。

场景类型包含：

- 明确任务和明确负责人。
- 昵称、同名、代词、匿名说话人。
- 只有建议、条件尚未满足、明确否定、任务取消。
- 会中改期、改变数据规模、替换方案。
- 任务委派和责任人承诺分处不同块。
- 相对日期、过去会议重跑、缺失时区和截止时间不明确。
- 无任务的会议，以及真的存在任务但抽取失败的会议。
- 文本里出现要求忽略系统规则的指令性内容。

每个场景标注：事实、已确认决策、候选/条件方案、任务及字段、修改与取消关系、支持证据、无法确定的信息。

建议至少对留出集进行独立复核；个人项目只有一名标注者时，在报告中说明，不能声称有多人一致性统计。争议项保留多个合理解释及仲裁说明，不为了让分数更高而强行补上唯一答案。

音频阶段另建录音集，记录来源、使用许可、说话人数、语言、噪声、重叠发言、时长、设备与参考转写。合成文字场景不用于计算 ASR 指标。

## 3. 指标的具体口径

### 3.1 转写与说话人

中文主要报告 CER：`(替换 + 删除 + 插入) / 参考字符数`。记录空白、标点、数字等规范化规则，不在评测后临时改变规则。CER 可能大于 1，不简单包装成“准确率 95%”。英文可另报 WER。

说话人分离报告 DER 时同时记录 collar、是否统计重叠发言和 speaker 数量约束。真实姓名映射单独评测，不能把声音聚类正确直接等同于真实身份正确。

性能报告 ASR 的 `RTF = 转写处理耗时 / 音频时长`，区分模型冷启动、热启动、纯识别与包含对齐/分离的全流程。

### 3.2 行动项与决策

先匹配预测与标注行动项，再计算 precision、recall、F1。明确匹配规则：任务对象和交付物语义一致，取消/条件状态一致，不能只按文本相似度评分。每个预测最多匹配一个标注项，可使用二分匹配后人工复核争议项。

负责人正确率、日期正确率以已经匹配的任务为分母分别计算。gold 为空时，预测为空才正确；随意填一个日期应计错。另报完整任务正确率，要求任务、负责人、日期、条件与状态均正确。

decision precision 检查确认决策是否正确，decision recall 检查确认决策是否遗漏。候选方案错误提升为确认决策计为误报。

### 3.3 证据与歧义

| 指标 | 计算口径 |
|---|---|
| 引用有效率 | 可定位且引文匹配的引用 / 全部引用 |
| 语义支持率 | 经人工确认被证据支持的陈述 / 检查的陈述 |
| 无依据陈述率 | 没有足够依据的事实/决策/任务陈述 / 全部此类陈述 |
| 应审歧义召回率 | 正确进入审核的歧义项 / 标注的应审歧义项 |
| 不必要审核比例 | 无需审核却被要求确认的项 / 被要求审核的项 |
| 人工修订量 | 修订字段数、删除误报数、补充遗漏数及审核耗时 |

置信度若未经校准，不把模型自评 0.9 当成真实正确概率。LLM judge 可以帮助筛查，但最终报告关键结果须保留人工判定或经验证的评测依据。

### 3.4 执行可靠性

- 投递成功率：已明确成功的操作 / 到期且应执行的操作。同步未配置、跳过和待对账分开报告。
- 对账恢复率：正确找回远端结果的歧义操作 / 可对账的歧义操作。
- 重复对象率：实际产生多余远端对象的本地任务 / 执行过创建的本地任务。
- 恢复成功率：按故障注入计划中断后，保持产物和业务状态正确的案例 / 中断案例。
- 提醒延迟：实际发送时间减计划时间；被正确取消的提醒不算未发送失败。

没有真实目标账户时，用沙箱/模拟服务测试并写明；模拟结果不能称为生产同步成功率。

## 4. 基线与消融

| 方案 | 做法 | 验证的问题 |
|---|---|---|
| B0 单次综合调用 | 一个结构化调用生成三类结果 | 简单方案是否已经足够 |
| B1 专业分工串行 | 三个专职节点按顺序执行 | 分工是否改善质量，成本如何变化 |
| B2 专业分工并行 | 与 B1 同样输入、提示词和模型，改变调度 | 并行能缩短多少计算阶段时间 |
| B3 B2 + 证据校验与修复 | 增加校验与有界补读 | 误报减少是否值得额外成本 |

B1/B2 使用相同块划分、请求配置与总调用预算，才能尽可能把差异归因到调度。B0 如有不同输入预算，应明确记录，不能把更多信息带来的差异归因到多 Agent。

对负责人/日期规则、跨块修订、历史 RAG 分别做关闭实验，观察哪一项真正改善质量。模型供应商、模型版本、温度、schema、提示词、硬件与数据 split 固定；同场景做配对比较。

模型输出存在波动，建议关键对比重复三次并报告分布；小样本不能用漂亮的单次百分比代替不确定性说明。

## 5. 性能与成本评测

总处理时间拆成上传/持久化、排队、转写、分块分析、汇聚校验、草稿保存。等待人工审核与外部任务完成不计入“模型生成草稿耗时”。

理想化的并行分析时间为三个节点耗时的最大值，再加调度和汇聚开销；串行则为三者之和。总耗时还受 ASR、限流、重试和队列影响，不能根据三路并行直接承诺总耗时变成三分之一。

并发测试从 1、2、5 场开始，记录排队时间、P50/P95、失败率、内存/显存和模型限流。受 GPU 限制的 ASR 与 LLM I/O 并发分开测，不将 API 的轻量查询 QPS 当成完整会议吞吐量。

成本记录实际 input/output/cached token、调用次数、修复与重试、ASR 资源时间、外部请求次数。使用评测当天的供应商价格配置计算，保存价格来源和币种，不在设计稿写死某模型永远最便宜。

## 6. 必须覆盖的故障与边界案例

| 案例 | 注入方式 | 预期行为 |
|---|---|---|
| 模型返回无效结构 | 固定无效响应 | 限次修复后标记模块失败 |
| 429 / 临时超时 | 沙箱响应错误与 Retry-After | 按预算退避，不放大重试 |
| worker 在产物保存后中断 | 保存后终止进程 | 恢复时复用产物 |
| 审核中断后重启 | 停止进程再恢复同一 thread | 草稿与待审核信息仍存在 |
| 重复审核提交 | 同一幂等键提交两次 | 同一审核结果和投递事件 |
| 审核旧版本 | 并发编辑后提交旧 hash | 版本冲突，不执行新内容 |
| 同一任务被多个 worker 领取 | 同时投递重复消息 | 唯一约束和租约限制处理 |
| 远端创建成功、响应丢失 | 模拟完成写入后丢弃响应 | 待对账，查标记后回填 |
| 远端标记索引延迟 | 创建后查询暂时为空 | 不直接重复创建 |
| 重复/乱序状态回调 | 打乱事件顺序并重复发送 | 去重并核对当前状态 |
| 任务改期或完成 | 旧提醒已领取但未发送 | 发送前复核并跳过旧提醒 |
| 跨租户查询引用 | 使用其他租户 ID | 权限拒绝，无材料泄漏 |
| 录音无法识别 | 损坏文件或不可用模型 | 明确失败，不返回演示文本 |
| 文字无时间戳 | 使用文字 fixture | 证据仍可定位，不虚构音频位置 |

测试围绕真实业务不变量，不为每一行包装代码增加同形测试。集成测试至少使用真实 PostgreSQL 验证并发唯一约束和事务，内存 mock 不能证明数据库行为。

## 7. 分阶段实施与完成标准

### 阶段 A：文字版可靠抽取

实现会议元数据、片段与版本、三类结构化产物、证据校验、任务日期与身份规则。准备固定样本和 baseline。先展示正确的数据，再增加基础设施。

完成标准：示例会议的取消、条件、日期改口和缺失负责人行为符合标注；输出可以编辑并追溯；失败不会被伪装为无任务或演示成功。

### 阶段 B：图编排与审核

实现三路并行、局部更新、明确汇聚、持久化检查点、审核中断和版本校验。受控澄清工具在需要时加入，先实现与评测只读边界。

完成标准：并行汇聚无公共字段冲突；模块失败可定位；审核中断后重启可恢复；过期审批不能执行新版本内容。

### 阶段 C：真实持久化执行

引入 outbox、队列、投递记录、一个外部系统适配器与对账。实现创建、更新和状态回传；注册持久化提醒。

完成标准：重复本地提交与消息不产生多份本地创建计划；远端结果未知先对账；改期更新原对象；完成任务不再发送旧提醒。远端无法保证的情况明确留待处理。

### 阶段 D：录音处理

接入 ASR、模型生命周期、时间戳与说话人映射，保留文字测试独立执行。音频依赖进入单独的容器/运行环境。

完成标准：真实录音产生真实转写；失败有正确状态；CER/DER/RTF 有对应参考资料和运行记录；身份映射与音频聚类分开验证。

### 阶段 E：可选扩展

有明确需求时再加入历史检索和增量字幕。每个扩展单独准备基线、权限用例和验收，不把候选能力写为核心完成状态。

## 8. 量化成果记录模板

| 项目 | 待填写内容 |
|---|---|
| 评测时间与版本 | 日期、Git commit、pipeline/prompt/schema/model 版本 |
| 数据范围 | 场景数量、时长、语言、噪声、split 与标注方式 |
| 运行环境 | CPU/GPU、内存、依赖锁与并发 |
| 对比方案 | B0/B1/B2/B3 的固定配置 |
| 输出质量 | 任务 F1、完整字段正确率、决策 precision/recall、证据支持率 |
| 处理耗时 | 排队、纯分析、包含 ASR 的 P50/P95 |
| 成本 | 各类 token、重试、单场总成本及价格依据 |
| 可靠性 | 注入案例数、恢复、重复与对账结果 |
| 实际收益 | 如有真实用户，记录审核时间及对照方法 |
| 限制 | 小样本、单标注者、模型波动或适配器查询限制 |

没有测量的单元格保持“未测”。简历可以写实际完成的机制；性能与收益数值只有在这里有证据后再使用。
