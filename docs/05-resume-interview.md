## 8. 项目追问与回答依据

### Q1：为什么拆成多个 Agent？一个提示词不够吗？

初步纪要、行动项与风险有不同的输出契约，分工便于各自校验和调试，也提供并行机会。但多个调用会增加 token 和工程成本，质量不自动更好。项目应保留综合调用基线，用固定样本比较，若简单方案足够就没有必要强拆。

追问准备：展示 B0/B1/B2 的质量、成本和耗时，而不是只背“专业化提高准确率”。

### Q2：这到底是 Agent 还是工作流？

主流程是显式工作流，ASR 和外部执行属于服务。语义节点负责不同任务，受控澄清子流程在允许的只读工具之间选择并观察结果，具有有限 Agent 行为。如果只实现固定模型调用，就准确称为工作流驱动的多节点 AI 应用，不宣称自主规划。

### Q3：为什么选 LangGraph，不直接 asyncio.gather？

只需要一次并行调用时 gather 更简单。这里还需要状态路由、模块产物、人工中断和检查点恢复，图结构更便于表达这些生命周期。框架本身不会自动解决业务幂等和外部对账，这些仍需数据库与适配器。

### Q4：并行节点为什么不能返回整份 state？

返回的键都会作为状态更新。同一步多个节点返回 meeting_id 等相同公共键，会让没有 reducer 的字段发生冲突。因此每个节点只返回自己的产物字段，错误集合设置明确合并规则；阶段状态由串行控制节点写。

展示材料：一段节点局部返回代码，说明错误 ID 如何避免重放重复。不要把这个问题只说成线程加锁。

### Q5：三个节点怎么保证都完成后再汇聚？

用多起点边明确等待 summary、actions、insights。每个分支在可恢复故障下返回模块 outcome，validator 决定哪些失败阻止发布、哪些允许部分草稿。原仓库相同深度的边不能简单断言一定重复触发；新版通过显式等待减少后续扩图时的歧义。

### Q6：一份 JSON 解析成功，怎么保证内容正确？

分别检查结构、引用和语义。Pydantic 只校验字段；引用校验检查原文范围与版本；语义校验检查否定、条件和陈述支持，关键结果保留用户核对。模型校验器也可能出错，评测应有人工作为依据。

### Q7：长会议为什么不能先摘要，再从摘要抽任务？

摘要会压缩信息，可能省掉责任人、时间和后续改口。行动项独立从分块原文提取，合并时再处理重复、取消和修订；纪要可以分层归并，但引用始终追到原片段。

### Q8：分块之后，一句“改到周三”怎么知道改哪项？

结合相邻上下文、明确姓名、任务对象和先前证据寻找关联候选。只有一个合理匹配时记录修订；存在多个候选时进入审核。保留旧日期与修改来源，不能只把最后一次出现的日期覆盖所有任务。

### Q9：相对日期怎么计算？

使用会议开始时间和会议时区作为固定基准，规则明确“下周”的自然周含义。模型提取时间原话，日期规则归一化。重跑历史会议时结果不随当天日期变化。只有日期时不发明时分秒。

演示：fixture 在 2026-10-09 召开，“下周三”为 2026-10-14；以后重跑保持一致。

### Q10：说话人分离能直接知道这个人是李明吗？

不能。声音聚类与真实身份映射是两个问题。默认保留匿名 speaker 标签，用已确认映射解析“我”；昵称和同名保留候选。说话人质量与姓名映射分别评测，不能把聚类结果直接当负责人账户。

### Q11：人工审核后，为什么还需要版本校验？

用户看到的内容可能在提交期间被编辑或重生成。审核绑定 report_version、hash 和目标范围；执行前核对同一版本与权限，避免用户批准旧内容却执行新内容。审批 ID 的存在并不表示所有行动都被批准。

### Q12：工作流重启后如何继续？

用稳定 thread_id 与持久化 checkpointer 恢复执行，业务数据库保存版本和产物。恢复中断节点会重新执行 interrupt 前的代码，所以那里只做安全读取或幂等操作。产物已保存但检查点没保存时，凭输入与版本键复用产物。

### Q13：加个唯一键能保证 Jira 零重复吗？

唯一键约束本地并发，不能消除远端创建成功但响应丢失的歧义。通过远端关联标记查询结果，超时先进入对账；无法可靠查询时保留未知状态并人工处理。只能报告在指定测试范围内的重复结果，不承诺任意故障下恰好一次。

### Q14：为什么需要 outbox？

直接“先写数据库再发队列”有提交成功但投递失败的窗口。业务数据与 outbox 在同一个事务提交，后续投递器能补发。投递器发送成功但更新记录失败时可能重发，因此消费端仍需要幂等。outbox 解决本地事务与投递的连接，不让远端操作变成数据库事务。

### Q15：任务改期后怎么避免再创建一张任务单？

action_id 在修订中稳定，远端映射按任务和目标账户唯一。新 revision 生成 update 操作，引用原 remote_id，并撤销旧提醒。重新抽取时先匹配已存在任务，不能把文本 hash 或日期变化当成新的业务身份。

### Q16：多个 worker 与模型限流怎么协调？

工作任务用租约和唯一约束处理重复领取，模型调用受全局/租户并发与 token 预算限制。ASR 与外部投递分队列。记录排队与计算时间，尊重 Retry-After，避免多层重试成倍放大。

### Q17：某个 Agent 失败，流程还能完成吗？

看它是否是必要前提。ASR 失败则不能进行后续真实分析；洞察失败可保留纪要和任务草稿；行动项失败不能伪装成“没有任务”。运行、模块、报告、投递和任务进度分别有状态，明确部分可用范围。

### Q18：指标怎么测，样本从哪里来？

说明样本数量、开发/验证/留出划分、标注方式和冻结版本。任务 precision/recall 区分遗漏与误报，负责人日期在匹配任务上单独评分；证据支持有人工作为依据。ASR 用真实录音和参考文本测 CER，不能用合成文字样本代替。

### Q19：并行是不是一定降低成本并加速三倍？

同样三个请求并行主要改变等待时间，不直接减少 token。分析阶段近似受最慢分支影响，总时间还含 ASR、排队、校验与限流。成本优化来自合理输入、缓存和减少不必要调用，应单独验证质量没有显著退化。

### Q20：你怎么防止转写中的指令触发工具？

把转写明确标为数据，澄清工具仅限只读、参数受会议范围验证，写入接口不向模型开放。发布计划来源于经过审核的业务字段。提示词只是约束的一部分，隔离通过代码权限与工具能力实现。

### Q21：历史 RAG 会不会把旧任务当成这次任务？

会有这个风险。历史材料带会议、时间、状态和引用，新会议任务抽取始终以当前转写为依据。历史检索用于解释背景或发现冲突，标明是历史证据；检索与生成都受权限控制。未实现时只作为后续方向讲解。

### Q22：你说的实时处理具体指什么？

分别说明上传、后台任务状态通知、增量 ASR 和实时草稿。会后上传处理不能叫实时字幕；WebSocket 接收音频也不意味着模型在持续转写。若只完成离线录音版，就准确描述为会后处理。

### Q23：为什么不用微服务和 Kubernetes？

个人项目先采用模块化单体、API 与 worker 分离，让数据、模型质量和可靠性闭环可验证。多个 Agent 不代表需要多个服务。出现独立资源、扩缩容或部署边界后再拆分，不为简历关键词增加无关组件。

### Q24：有哪些还没解决的问题？

根据实际完成情况回答：说话人重叠和身份歧义、校验模型误判、跨块关联不确定、远端查询标记延迟、样本规模较小等。指出已有处理边界和下一步实验，不编造“企业级已全面解决”。

## 9. 三个 STAR 讲法

### 场景一：重构项目架构

S：学习开源会议助手时，发现流程拆分合理，但部分功能停留在示例和文档层。

T：将相同业务主线做成能够验证的 Python AI 应用，重点是任务正确性和流程可靠性。

A：固定输入版本；按纪要、行动项与风险分工；绑定原文；增加校验、审核与恢复；建立基线评测。

R：填写实际完成的模块、演示与评测。如果只完成方案，就说形成了设计和实施契约；开发完成后再说完成了可运行闭环。

### 场景二：外部创建结果不确定

S：在测试中模拟远端已经创建任务，但客户端没有收到响应。

T：避免简单重试带来重复任务，并让系统能解释当前同步状态。

A：稳定 action_id、本地唯一约束、远端关联标记、投递尝试与待对账状态；恢复后查询远端并回填。

R：填写真实故障注入结果及目标系统查询限制。不能把设计推导写成生产零重复。

### 场景三：模型把条件方案误当决策

S：固定场景中出现“压测通过后才考虑发布”，普通摘要可能遗漏条件。

T：保留候选状态，避免自动创建确定的发布任务。

A：在 schema 中分开 proposed/conditional/committed，保留证据和 conditions，并对关键陈述做校验与审核。

R：展示对应输入、预期输出、真实模型输出与修复效果；用留出集结果说明是否改善，未测时不填百分比。

## 10. 面试准备清单

准备一套可以连续展示的材料：架构图、示例输入与草稿、节点局部更新代码、版本审核、恢复日志、外部对账状态、评测配置和结果。
