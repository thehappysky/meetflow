# 事项身份与状态审查改进

日期：2026-11-14。基于CP4保留的失败继续开发，不删除失败，不改既有业务预期。当前主服务仍运行state_v2，候选先隔离实测。

## 本轮要解决的问题

1. 同一演示的“安排”和“暂停”被按task字符串分到两个桶，审查者只看桶内证据，无法发现旧待办已经被暂停。
2. cancelled状态计算正确，但审查仍用“是否存在有效承诺”否定历史取消记录，导致整个事项被压入疑点。
3. 一句发言的两个动作共享第一人称主语，第二项却丢失姓名。上传账号不能用于填补这个姓名。

## 实现前登记的候选

保持提取、覆盖、归并、审查四种职责，用相同本地4B、temperature=0、seed=2026、6步/1536输出/48次总调用预算对照。

- `context_v3`：从显式原文署名提供speaker_hint，仅作为文本标签而非实名识别；提取模型选择speaker/named/unknown责任来源，由代码回填姓名，不自动把发言人当负责人。不同task名称时，归并职责先执行一次身份关联子任务，按原文将提及分组，不能遗漏/重复分配，不能靠“暂停/取消”关键词直接批量改状态。原逐事项字段归并和独立审查继续保留。
- `review_v3`：在context_v3基础上，审查模型独立选择当前状态（含暂停/取消/完成/未确认建议/非事项），以及负责人/日期/条件的依据ID；代码比较建议值与实际归并值，生成字段争议。移除“当前仍需履约”与“历史事项是否应追踪”共用一个模糊布尔判断的歧义。审查不能直接改正式事项，分歧仍有限返工/人工确认。

新版本写入运行manifest，旧state_v2及更早协议保持。不是给三个失败例写规则命中，也不扩大资料权限。与当前15例全量开发回归比较，先看全案例正确数及具体严重退步，再看模型请求、token、时延和疑点。新加否定取消/取消的是实际交付工作/不同演示/代办负责人等边界检查；由代理编写，不能称独立人工金标准。所有候选失败、源码、输入、模型响应分别保存。
